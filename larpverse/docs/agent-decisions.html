Agent decision points in the search mission

The brief keeps control, localisation and scan maths local. So the agent does not fly drones or do Bayes updates. It chooses between options that the numeric code has already scored, using information the formulas can't weigh, and it explains each choice. A validator checks every choice, and the numeric planner takes over if the agent fails.

Numbers proposeThe planner lists the actions it can take, each with expected information gain, travel, battery and risk flags.
Agent decidesIt picks one, using context the formulas lack: operator intel, competing leads, faults, flagged sites. It writes the reason down.
Code verifiesThe pick must be a listed option within hard limits. Otherwise the numeric fallback runs, and the log says so.

Recommendation

Build one agent: the Mission Commander

It has three entry points. Together they cover the five MVP opportunities, and all of them hook into code that already exists.

  1. Intake (C). Turns the incident commander's notes into prior weights, no-go zones and sounds to ignore, shown on the map for approval.
  2. Decide (A, B, I). Runs at every Coordinator._decide() call. It picks from the planner's top options: relocate, extend dwell, chase a lead, stop, or report insufficient evidence.
  3. Brief (D). Writes the rescuer handover and answers "why did d3 move?" from the decision log.
About 5 hours for one person

This puts a real decision on camera at the brief's central moment: ambiguous scans, then an autonomous relocation. The video can show the option table, the pick and the reason.

It also covers what a pure information-gain formula misses: "bedrooms were on the east side", a drone at 30% battery, a slab flagged unstable, an acoustic lead with no radar return.

It's safe to demo. The sim clock pauses while the agent thinks, every pick is validated, and a record/replay mode means the live demo doesn't need the network.

How it plugs in

One hook, one validator, one fallback

Coordinator_decide() fires after each scan, fault or operator message. The sim clock pauses.
Planner optionsplanner.options(k=5) returns scored actions: EIG (nats), travel, battery after, site flags, lead.
Mission CommanderReads a context built from state.json (no ground truth). Tools: preview, scan detail, site detail, commit.
ValidatorChecks the option id exists, battery stays at or above 25%, no-go zones, claim wording, and a 20 s limit.
Command + logSends the contract command and appends to decisions[] in state.json. The dashboard shows the card.

If the agent times out, returns something invalid or breaks a rule, the coordinator runs the planner's top option. It logs by: "fallback" with the reason. The mission never waits on the network.

Keep away from the agent

What the agent never touches

  • Ground truth. Context is built from state.json only, and a test asserts that no targets key reaches the prompt.
  • Trajectories, motor commands or anything inside the control loop.
  • The Bayes update and likelihood maths. It can ask to down-weight a scan, never to add evidence.
  • Claims. It can't output "confirmed" or "survivor found". Candidates stay candidate search regions.
  • Inventing options. It picks an id from the list, or the fallback runs.
Prove it adds value

How to evaluate it honestly

  • Run three policies on the same seeds and scan budget: fixed sites, EIG argmax and agent.
  • On pure geometry, expect the agent to roughly match argmax. That's fine, so say so.
  • Add scenario packs where context matters:
    • correct and misleading operator intel
    • low battery
    • an acoustic lead with no radar return
    • an unstable site
    • a periodic non-human distractor
  • Report localisation error, 95% coverage, scans used, false alerts, battery violations, how often the agent overruled argmax and what happened when it did, fallback rate and latency.
